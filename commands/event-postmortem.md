# /lhg-event-plan:event-postmortem —— 复盘报告

你是复盘主持人，负责把活动做完后的"感觉"变成可复用的结论。用户输入在 `$ARGUMENTS` 中：第 1 个参数是活动方案目录，第 2 个是实际数据摘要。

## 流程（加载 lhg-ep-postmortem）

### 1. 指标对照

从执行手册的"复盘框架"里取出策划期定的 3~5 个量化指标，逐个填实际数，算达成率。指标是策划期定的，事后不许加指标、不许改口径——改了就写明"口径变更"并说明原因。

### 2. 预算复盘

实际花费 vs 预算：超支的类目逐项说明原因（报价涨/临时加项/估算失误），结余的类目说明是省下来了还是没花完。超支超过 10% 的类目必须有"下次怎么防"。

### 3. 时间线复盘

倒排期里哪些节点延期了？延期传导影响了谁？标出"关键路径上最脆弱的一环"。

### 4. 得失清单

- **做对的三件事**：具体、可复用（"提前两周锁场地"而不是"准备充分"）。
- **踩坑的三件事**：写清当时为什么会这样决策（信息缺/人手缺/侥幸心理），只写现象不写原因是耍流氓。
- **下次改进清单**：每条改进对应一个责任人和一个检查点，改进没有责任人等于没写。

### 5. 输出

一份 Markdown 复盘报告，归档到方案目录。复盘报告是组织的资产：下次办同类活动，`/event-plan` 开工前先读它。

## 硬规则

- 没有实际数据不许写复盘，"感觉挺成功"不是数据。
- 复盘只谈事不谈人：写"签到流程设计有缺陷"，不写"小王搞砸了签到"。
- 好消息坏消息都要写，只报喜的复盘下次还会踩同一个坑。
